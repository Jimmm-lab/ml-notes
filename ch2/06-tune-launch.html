Grid Search：把組合全部試一遍

投影片 32–33

第 5 篇的隨機森林用的是預設超參數。你可以手動改一個、跑一次交叉驗證、再改一個……但這很花時間，也很難試得完整。投影片的建議是讓 GridSearchCV 代勞：你列出每個超參數想試的值，它把所有組合都用交叉驗證評估一遍。

from sklearn.model_selection import GridSearchCV

param_grid = [
    {'n_estimators': [3, 10, 30], 'max_features': [2, 4, 6, 8]},
    {'bootstrap': [False], 'n_estimators': [3, 10], 'max_features': [2, 3, 4]},
]
forest_reg = RandomForestRegressor()
grid_search = GridSearchCV(forest_reg, param_grid, cv=5,
                           scoring='neg_mean_squared_error',
                           return_train_score=True)
grid_search.fit(housing_prepared, housing_labels)

param_grid 是一個清單，裡面有兩張「格子」。第一張：n_estimators（幾棵樹）3 種 × max_features（每次切分隨機看幾個特徵）4 種 = 12 組，bootstrap 用預設值 True。第二張：把 bootstrap 關掉，再試 2 × 3 = 6 組。

總共訓練幾次？18 組 × 5 折 = 90 次，這是投影片的數字。但 GridSearchCV 預設 refit=True：找到最佳組合後，還會用整個訓練集再訓練一次，放在 best_estimator_。所以實際是 91 次。

return_train_score=True：順便記下每組在訓練折上的分數，才能像第 5 篇那樣比較訓練與驗證的差距。

下面是投影片 33 上 18 組的驗證 RMSE，顏色越深越好。點任一格看細節：

格內數字為 5 折驗證 RMSE（千美元），顏色越深越好；mf = max_features，欄是樹的數量。

最佳組合的 RMSE 是 49,682，比第 5 篇預設隨機森林的 50,182 好一點點（第 5 篇用 10 折、這裡用 5 折，只能粗略比較）。值得注意的是它只用 30 棵樹，第 5 篇的預設是 100 棵。差別在 max_features：迴歸森林的預設值會讓每次切分都看全部 16 個特徵，樹與樹很像；這裡每次只看 8 個，樹更不一樣，依第 5 篇的推導，相關係數 ρ 越小，平均的效果越好。從熱圖還能讀出三件事：

最佳值落在格子的邊緣。max_features=8 和 n_estimators=30 都是我們給的最大值。這通常代表再往外擴還可能更好，課本也建議接著試更大的值。只要最佳值卡在邊界，就該把範圍往那個方向延伸再搜一次。

樹越多越好，但好得越來越少。每一列從 3 棵到 10 棵進步很多，10 到 30 就只剩一點。這正是第 5 篇推導的結果：變異數隨 下降，最後卡在 的底線。

best_score_ 是負的 MSE。跟 cross_val_score 一樣，要先加負號、開根號才會變回 RMSE。

bootstrap=False 的訓練分數會洩漏什麼？投影片沒有列出訓練分數，所以我用目前版本的 Scikit-Learn 重跑了一次。bootstrap=False 的 6 組，訓練 RMSE 全都接近 0，驗證卻在 51,300 到 62,400 之間。原因是每棵樹都拿到完整的訓練集、而且長到底，每一棵都像第 5 篇那棵單一決策樹一樣把答案背了下來，平均起來當然還是背答案。不過因為 max_features 讓每棵樹看的特徵不同，它們的驗證分數仍然比單棵樹的 71,408 好得多。真正的教訓是：這時訓練分數完全看不出模型過擬合到什麼程度，只能看驗證分數。bootstrap=True 的最佳組合則是訓練約 19,500、驗證約 49,900，雖然還是有差距，但沒有背起來。

Randomized Search：搜尋空間大時的選擇

投影片 34

Grid search 適合只有少數組合的情況。超參數一多、每個又有很多可能值時，組合數會用乘的爆炸。這時改用 RandomizedSearchCV：每次從你給的分布隨機抽一組超參數，總共抽 n_iter 次。

from sklearn.model_selection import RandomizedSearchCV
from scipy.stats import randint

param_distribs = {
    'n_estimators': randint(low=1, high=200),
    'max_features': randint(low=1, high=8),
}
rnd_search = RandomizedSearchCV(forest_reg, param_distributions=param_distribs,
                                n_iter=10, cv=5, scoring='neg_mean_squared_error',
                                random_state=42)
rnd_search.fit(housing_prepared, housing_labels)

投影片列了兩個好處：每個超參數會試到很多不同的值，而不是格子上那幾個；而且只要設定 n_iter，就能直接控制要花多少運算預算。小提醒：投影片說跑 1,000 次就會試 1,000 個不同的值，前提是分布是連續的。像上面 randint(1, 8) 只有 1 到 7 共 7 種可能，抽再多次也只會重複這 7 個值。這段是課本的原始程式碼，而它的上限 7 還比 grid search 找到的最佳值 8 小，自己用時記得把範圍開大到 16（全部特徵數）。

實驗：格點 vs 隨機

假設有兩個超參數，但只有橫軸那個真的影響分數（上方曲線），縱軸那個幾乎沒影響。這在實務上很常見。用同樣的試驗次數比較兩種搜尋：

重要的超參數試了幾個不同值—
這次找到的最佳分數—
隨機搜尋平均能找到（2,000 次模擬）—

推導：隨機搜尋要試幾次才夠？

把所有可能的超參數組合依驗證分數排好，問：隨機試 次，至少有一次落在「前 5% 最好的區域」的機率是多少？

第 1 步：一次沒中的機率

每次抽樣獨立，落在前 5% 的機率是 ，所以一次沒中是 。

第 2 步：n 次全都沒中

第 3 步：至少中一次，並要求它 ≥ 95%

所以只要 59 次，就有 95% 的機率碰到前 5% 的組合，而且這個數字跟超參數有幾個完全無關。Grid search 則相反：每多一個超參數，組合數就再乘上一次。另一個好處是上面實驗展示的：格點上重要的超參數只試了 個值，隨機搜尋則試了 個不同的值。這個觀點來自 Bergstra 與 Bengio（2012）的論文。

推導：特徵重要度怎麼算？

Scikit-Learn 的 feature_importances_ 是 MDI（Mean Decrease in Impurity）。它沿用第 5 篇決策樹的切分準則。

第 1 步：每一刀讓不純度降了多少

節點 有 筆資料，被切成左右兩邊。這一刀的貢獻是加權的 MSE 下降量：

每一項的 MSE 都乘上該節點的資料筆數，所以越靠近根部、經過越多資料的切分，貢獻越大。括號裡剛好等於 ，其中 就是第 5 篇決策樹挑選切分時最小化的加權 MSE：CART 挑的那一刀，正是讓這一項最大的那一刀。

第 2 步：一棵樹裡，把用到特徵 j 的切分加起來，再正規化

第 3 步：對森林裡所有樹取平均

所以重要度總和一定是 1。投影片前 9 名加起來是 0.942，剩下 7 個欄位合計只有 0.058。

為什麼 pop_per_hhold 的 r 幾乎是 0，卻這麼重要？

我用完整資料查了一下：每戶人口數的中位數是 2.8 人，第 99 百分位是 5.4 人，但最大值是 1,243 人，顯然是宿舍、營區或資料錯誤。Pearson r 用的是離均差的乘積，這幾個極端值就把它拉得接近 0。

算法r說明
Pearson（全部資料）−0.024第 3 篇看到的數字
Pearson（去掉最大的 1%）−0.280只拿掉 1% 的資料，強度就變成十倍
Spearman（用排名算）−0.257只看大小順序，不受極端值影響

把街區依每戶人口數分成 10 等份，房價平均從最低組的約 26.6 萬一路降到最高組的約 14.4 萬，關係其實很清楚：越擁擠，房價越低。決策樹切分時只看「大於或小於某個門檻」，跟第 4 篇的中位數一樣只在乎排序，極端值再大也只是落在最右邊那一組，所以森林看得到這個規律，Pearson r 卻看不到。這也再次印證第 3 篇的結論：r 只是快速掃描的工具，不能拿來判定一個特徵沒用。

MDI 的限制：它是在訓練資料上算的，而且偏好可以切很多刀的連續特徵，對只有 0／1 的 one-hot 欄比較吃虧。要更可靠的排名，可以用 sklearn.inspection.permutation_importance：在驗證資料上把某一欄打亂，看分數掉多少。另外，重要度只代表模型怎麼用這個特徵，不代表因果。

投影片 36

調好模型之後，終於可以打開第 2 篇鎖起來的測試集：

推導：RMSE 的 95% 信賴區間

第 1 步：把 MSE 看成「平方誤差的平均」

令 ，則 。測試集有 筆，依中央極限定理， 近似常態分布。

第 2 步：用 t 分布算平均數的區間

是 的樣本標準差。 這麼大時，。

第 3 步：兩端開根號

開根號是遞增函數，不會改變大小順序，所以把 MSE 區間的兩個端點各自開根號，就是 RMSE 的區間。

from scipy import stats

squared_errors = (final_predictions - y_test) ** 2
np.sqrt(stats.t.interval(0.95, len(squared_errors) - 1,
                         loc=squared_errors.mean(),
                         scale=stats.sem(squared_errors)))

投影片沒有附上這一步。我用目前版本的 Scikit-Learn 從頭重跑整個流程，得到測試 RMSE 47,873，95% 信賴區間約為 45,893 到 49,775，也就是正負兩千美元左右。你自己跑的數字可能略有不同，因為不同版本切出的訓練集和隨機森林的亂數都不一樣。

為什麼測試分數通常比交叉驗證差？

投影片提醒兩件事。第一，如果做了大量調參，測試分數通常會比交叉驗證稍差一點，因為系統最後是被調成「在驗證資料上表現好」。第二，就算差了，也不要回頭調超參數去讓測試分數好看，那些改進不會推廣到新資料上。

這裡有一個小陷阱：joblib 存的是物件，不會存類別的程式碼。自訂的 CombinedAttributesAdder 必須在服務端也 import 得到，否則讀檔會失敗。

上線不是結束

投影片強調，還要寫監控程式，定期檢查系統上線後的實際表現，表現下滑就發出警報。模型不會自己壞掉，但世界會變：房價漲了、新的社區蓋起來了，這叫資料漂移（data drift），模型會慢慢「腐爛」。如果資料持續變化，就要定期更新資料集、重新訓練模型，而且盡量全部自動化：

  1. 定期蒐集新資料並標註例如每月拿到最新的實際成交價
  2. 自動訓練並微調超參數本篇的 GridSearchCV 整段寫成腳本
  3. 在更新後的測試集上比較新舊模型兩個模型用同一份新測試集評分
  4. 新模型沒變差才部署變差就保留舊模型，並通知人來看

課本另外建議：也要監控輸入資料的品質（缺值突然變多、某欄的分布偏移），並保留每一版的模型和資料集，出問題時才能快速回滾到上一版。

實驗：要不要自動重新訓練？

模擬一個上線 36 個月的模型，房價分布每個月慢慢漂移。比較三種維護策略（模擬資料）：

36 個月平均 RMSE—
重新訓練次數—
超過警戒線的月數—
每月 RMSE警戒線（上線時 RMSE +15%）重新訓練

放著不管，誤差會一路往上爬。固定排程最簡單，但它不看狀況：漂移慢時白白多訓練幾次，漂移快時仍會超線好幾個月。依監控觸發會跟著實際狀況調整，漂移慢就少訓練、漂移快就多訓練；代價是它一定要等誤差真的超線才反應，所以總會有幾個月超線。而且前提是你真的有在監控，也能及時拿到新的標籤。

Python 實作：本篇完整流程

import joblib
import numpy as np
from scipy import stats
from scipy.stats import randint
from sklearn.ensemble import RandomForestRegressor
from sklearn.metrics import mean_squared_error
from sklearn.model_selection import GridSearchCV, RandomizedSearchCV
from sklearn.pipeline import Pipeline

# housing_prepared, housing_labels, full_pipeline, num_attribs, strat_test_set：前幾篇的結果

# 1) Grid search：18 組 × 5 折 = 90 次，再 refit 1 次
param_grid = [
    {'n_estimators': [3, 10, 30], 'max_features': [2, 4, 6, 8]},
    {'bootstrap': [False], 'n_estimators': [3, 10], 'max_features': [2, 3, 4]},
]
grid_search = GridSearchCV(RandomForestRegressor(random_state=42), param_grid, cv=5,
                           scoring='neg_mean_squared_error', return_train_score=True)
grid_search.fit(housing_prepared, housing_labels)
print(grid_search.best_params_, np.sqrt(-grid_search.best_score_))

cv = grid_search.cv_results_
for tr, te, p in zip(cv["mean_train_score"], cv["mean_test_score"], cv["params"]):
    print(f"train {np.sqrt(-tr):8.0f}  val {np.sqrt(-te):8.0f}  {p}")

# 2) Randomized search：用 n_iter 控制預算
rnd_search = RandomizedSearchCV(RandomForestRegressor(random_state=42),
                                {'n_estimators': randint(1, 200), 'max_features': randint(1, 8)},
                                n_iter=10, cv=5, scoring='neg_mean_squared_error', random_state=42)
rnd_search.fit(housing_prepared, housing_labels)

# 3) 特徵重要度（MDI），名稱順序要跟流水線一致
final_model = grid_search.best_estimator_
extra_attribs = ["rooms_per_hhold", "pop_per_hhold", "bedrooms_per_room"]
cat_attribs = list(full_pipeline.named_transformers_["cat"].categories_[0])
attributes = num_attribs + extra_attribs + cat_attribs
for imp, name in sorted(zip(final_model.feature_importances_, attributes), reverse=True):
    print(f"{imp:.4f}  {name}")

# 4) 測試集：只 transform，只評一次
X_test = strat_test_set.drop("median_house_value", axis=1)
y_test = strat_test_set["median_house_value"].copy()
X_test_prepared = full_pipeline.transform(X_test)
final_predictions = final_model.predict(X_test_prepared)
print("test RMSE:", np.sqrt(mean_squared_error(y_test, final_predictions)))

sq = (final_predictions - y_test) ** 2
print("95% CI:", np.sqrt(stats.t.interval(0.95, len(sq) - 1, loc=sq.mean(), scale=stats.sem(sq))))

# 5) 存成一條完整流水線
joblib.dump(Pipeline([("preparation", full_pipeline), ("forest", final_model)]), "housing_model.pkl")

# 6) 上線後的監控：新標註資料的 RMSE 超過基準 10% 就警報
def check_live_performance(model, X_new, y_new, baseline_rmse, tolerance=0.10):
    rmse = np.sqrt(mean_squared_error(y_new, model.predict(X_new)))
    if rmse > baseline_rmse * (1 + tolerance):
        print(f"ALERT: live RMSE {rmse:.0f} > baseline {baseline_rmse:.0f}")
    return rmse

我在一台雙核心的測試機上跑，整段大約 4 分鐘：grid search 的 91 次訓練約 50 秒，最久的其實是隨機搜尋（樹最多到 200 棵），約 3 分鐘。在搜尋類別裡加上 n_jobs=-1 就能用上所有 CPU 核心，快很多。我用這段程式在目前的 Scikit-Learn 1.8 上實際跑過，最佳組合同樣是 max_features=8, n_estimators=30，特徵重要度前八名的順序也跟投影片一樣。

常見陷阱與自我檢查

對測試集呼叫 fit_transform會用測試集重新學補值與縮放參數，等於偷看考卷。只能 transform。
看了測試分數再回去調參測試集一旦參與挑選，就不再是公正的評估，分數會變得過度樂觀。
最佳值落在格子邊緣就收工max_features=8、n_estimators=30 都是上限，應該擴大範圍再搜。
把 best_score_ 當成 RMSE它是負的 MSE，要 np.sqrt(-best_score_)。
把特徵重要度當成因果它只說明模型怎麼用這個特徵，而且 MDI 偏好連續特徵，可以用 permutation importance 交叉確認。
只存模型、不存前處理上線時前處理對不上，預測就全錯了。整條 Pipeline 一起存。
param_grid 有兩張格子，分別是 3×4 和 2×3，cv=5，總共會訓練幾次？

(12 + 6) × 5 = 90 次交叉驗證，加上 refit=True 預設會用整個訓練集再訓練最佳組合 1 次，共 91 次。

超參數有 6 個，每個想試 10 個值，該用哪種搜尋？

Grid search 要 10⁶ = 一百萬組，乘上 5 折，不可能跑完。改用 randomized search，依推導大約 60 次就有 95% 的機率碰到前 5% 的組合。

測試 RMSE 比交叉驗證好，可以宣稱模型「其實更準」嗎？

不行。那可能只是運氣，加上最終模型多用了 25% 的資料。該回報的是測試分數本身和它的信賴區間，並說明調參過程可能讓交叉驗證偏樂觀。

模型上線半年後，監控發現 RMSE 上升 15%，第一步該做什麼？

先檢查輸入資料：是不是某欄的分布變了、缺值變多、上游格式改了。如果是真實世界在變（例如房價普遍上漲），就用新標註的資料重新訓練，並在新的測試集上跟舊模型比較，確定沒變差才部署。

整個專案一頁回顧

步驟一句話重點
1. 看清全局先問輸出給誰用，再決定任務類型與評估指標（RMSE vs MAE）。
2. 取得資料看完資料的基本狀況就立刻切出測試集，重要屬性用分層抽樣。
3. 探索資料只在訓練集上探索；相關係數只量線性關係，一定要搭配散佈圖。
4. 準備資料補值、編碼、縮放都寫成轉換器串成 Pipeline；只在訓練集上 fit。
5. 選模型、訓練用交叉驗證打分，看訓練與驗證的差距判斷欠擬合或過擬合。
6. 微調模型讓 Grid／Randomized Search 找超參數，再看特徵重要度找洞見。
7. 呈現成果測試集只評一次、附信賴區間，並把數字放回商業目標。
8. 上線、監控整條流水線一起部署，監控表現與輸入資料，重新訓練盡量自動化。
